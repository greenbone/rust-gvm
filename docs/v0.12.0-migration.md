# Migrating from v0.11.1 to v0.12.0

`v0.12.0` adds typed Active Directory operations, current structured Agent
Control scheduling, inventory-token issuance, richer inventory/report
projections, and protected report-result filtering. The project remains a
pre-1.0 Technology Preview, so this minor version carries the source-level
migrations described below.

Most existing GMP requests continue to compile unchanged. Applications that
construct or serialize agent schedules, modify agent groups, deserialize exact
response schemas, or compose report-result filters should review the relevant
sections.

## Structured agent schedules and group delay

`AgentScriptExecutorConfig::scheduler_cron_time` now contains
`Vec<AgentSchedule>` instead of `Vec<String>`. `AgentSchedule` contains a cron
string and optional `max_delay_seconds`:

```rust,ignore
use gvm_gmp::AgentSchedule;

let schedules: Vec<AgentSchedule> = old_cron_strings
    .into_iter()
    .map(AgentSchedule::from)
    .collect();
```

Individual strings still support `.into()`. Requests always encode current
gvmd's nested `<item><cron>…</cron></item>` form. With the optional `serde`
feature, legacy string arrays remain readable, while serialization emits
structured objects. Request delays must be between zero and `i32::MAX`; an
omitted delay retains the server default of zero.

Agent-group create, modify, and read models expose `max_delay_seconds`.
`ModifyAgentGroupRequest::new` now requires the current nonempty name:

```rust,ignore
let request = ModifyAgentGroupRequest::new(group_id, current_name, cron);
```

Pass the observed group name when no rename is intended. On current gvmd,
omitting the delay during modification resets it to zero rather than preserving
the previous value; set it explicitly when retention is required. Scanner
responses can now expose `agent_control_config_defaults`.

## Active Directory operations

`CredentialType::ActiveDirectory` and `ActiveDirectoryCredentialFields` support
credential creation, partial modification, and non-secret response metadata.
Create and inline verification require host, bind DN, bind password, base DN,
and `ActiveDirectoryTlsMode`; omit the port to retain gvmd's LDAPS/StartTLS
default. Bind passwords remain write-only and are redacted from Debug and client
wire traces.

`VerifyActiveDirectoryCredentialRequest` separates saved and inline forms so
they cannot be mixed. `GetActiveDirectoryObjectsRequest` performs live
directory discovery without creating targets and returns typed counts,
truncation state, objects, optional computer details, and optional
target/task/configuration references.

These commands require positive XML-help discovery because GMP 22.x alone does
not prove that gvmd was built and configured with AD integration. Destination,
authorization, DN, LDAP, and TLS policy remain server-owned. Built-in mocks
reject live AD operations; explicit fixtures and scenarios can model outcomes
without connecting to LDAP.

## Agent inventory and support bundles

`GetAgentInventoryTokenRequest` returns a typed confidential token response.
Call `discover_commands()` before use: the command belongs to the agent-enabled
GMP 22.8 family but still requires positive help discovery. Access the token
through `response.token.as_str()`. Debug and wire tracing redact the token;
explicit serialization and raw payload access do not.

Successful responses with missing, empty, or whitespace-only token content now
fail typed response parsing. Nonempty opaque token content is preserved after
XML decoding and is not normalized or interpreted as a JWT.

`Agent` responses add optional `operating_system`, `architecture`, `os_cpe`,
and `os_status` fields. `GetAgentSupportBundleRequest::anonymized` is independent
of the existing encryption selector. Mock bundle payloads are inert fixtures;
they do not prove anonymization or encryption.

## Additional typed projections

Several non-exhaustive response models now preserve optional server metadata:

- `Target::source` and target create/modify source selection;
- `NvtRef::type_` alongside unchanged opaque `type_metadata`;
- `StructuredReportTask::scan_config` in scan and audit reports;
- report application `hosts_count`, `occurrences`, and `threat`;
- scanner Agent Control defaults and agent operating-system observations.

Older XML and serialized values without the new optional fields remain
readable. Newly serialized values include the additional fields, so exact JSON
snapshots or closed schemas may need updates. Unknown source/type strings remain
forward-compatible server vocabulary rather than locally normalized enums.

Sensor scanners now accept port `0`, matching current gvmd. Ordinary scanners
and network relays retain their existing nonzero-port rules. Changing scanner
types remains validated against the effective retained or replacement port.

## Protected report-result filtering

Use `compose_report_results_filter` when an endpoint must constrain results to
one report while accepting saved and/or inline filter term text:

```rust,ignore
let filter = compose_report_results_filter(
    &report_id,
    saved_filter_term.as_deref(),
    inline_filter.as_deref(),
    Pagination::new(page, per_page),
)?;

let request = GetResultsRequest {
    filter_string: Some(filter),
    filter_id: None,
    ..Default::default()
};
```

Leave `filter_id` unset because gvmd saved-filter selection replaces rather
than augments inline terms. The helper rejects caller-owned scope/pagination,
unsupported compound comparators, and unterminated quoted literals, then
appends independent `_and_report_id` isolation and pagination. Existing raw
filter escape hatches remain available and permissive.

## Compatibility and qualification boundary

The minimum supported Rust version remains 1.89. Tagged release artifacts keep
the v0.11 publication contract: five mock-server binary archives with
checksums, a Linux amd64/arm64 GHCR index, CycloneDX SBOMs and quality results,
and Sigstore provenance attestations. Only immutable `v`-prefixed tags are
published; there is no moving `latest` image.

The new AD, Agent Control, inventory-token, bundle, and filter behavior is
backed by pinned gvmd source/schema evidence and deterministic tests. It does
not claim live LDAP, Agent Controller scheduling, token signing,
support-bundle privacy/cryptography, or live-gvmd qualification.
